## 정답 및 해설

### Part 1

1. **O.** 컴파일러 최적화는 보통 알고리즘 자체를 바꾸지 않고, instruction 수·메모리 대기·branch 비용 같은 상수 인자를 줄인다.

2. **X.** 이 강의의 global optimization은 한 함수의 control-flow graph 전체를 다룬다. 여러 함수의 관계를 함께 보는 것은 inter-procedural analysis다.

3. **O.** 두 피연산자가 compile-time constant이므로 컴파일러가 실행 전에 `0xFF00`을 계산할 수 있다.

4. **X.** 수학적으로는 양수처럼 보여도 `a-b`가 signed overflow하면 C에서 정의되지 않은 동작이다. 컴파일러는 overflow가 발생하지 않는 경로를 전제로 조건을 참으로 최적화할 수 있다.

5. **O.** 정적 라이브러리는 object file 아카이브이며, 링커는 필요한 unresolved symbol을 해결하는 멤버를 가져와 링크한다.

### Part 2

6. 예시 핵심: preprocessing은 `#include` 등을 해소해 확장된 C 소스를 만든다. compilation은 C를 assembly로 변환한다. assembling은 assembly를 relocatable object file로 만든다. linking은 여러 object file과 필요한 라이브러리를 결합해 executable object file을 만든다. 별도 컴파일된 파일은 최종 배치 주소를 모르므로 참조와 주소를 나중에 고칠 수 있어야 한다. 이 재배치 가능성이 relocation의 출발점이다.

7. 예시 핵심: local optimization은 하나의 basic block 안에서 constant folding·local CSE 등을 수행한다. basic block은 single entry와 single exit를 갖는 최소 control-flow 단위다. global optimization은 한 함수의 control-flow graph와 loop nest를 대상으로 code motion·global CSE·dead code elimination 등을 수행한다. 따라서 여기서 global은 여러 함수 전체를 뜻하지 않는다. 함수 간 분석은 가능한 호출 대상, 별칭, side effect, 입력을 더 넓게 추적해야 하므로 비용과 복잡도가 커진다.

8. 예시 핵심: constant folding은 상수식의 결과를 미리 계산한다. strength reduction은 비싼 연산을 더 싼 동치 연산으로 바꾼다. dead code elimination은 절대 실행되지 않거나 결과가 덮어써지는 계산을 제거한다. CSE는 같은 부분식을 한 번 계산해 재사용한다. 네 변환 모두 동일한 입력에서 관찰 가능한 출력과 side effect를 보존해야 한다. 그렇지 않다면 최적화가 아니라 프로그램 의미 변경이다.

9. 예시 핵심: code motion은 옮길 식이 반복마다 같은 결과를 내는 loop invariant일 때만 안전하다. 호출의 정의나 side effect를 현재 compilation unit만으로 완전히 모를 수 있다. 포인터 별칭 때문에 호출 또는 루프 본문이 관련 메모리를 바꿀 가능성도 고려해야 한다. 모든 함수를 함께 분석하면 더 많은 사실을 알 수 있지만 inter-procedural 분석 비용이 크다. 사람이 `strlen`과 문자열 변경의 관계를 확인한 뒤 고치는 것과 컴파일러가 일반적인 C 함수 호출에 대해 증명하는 것은 다르다.

10. 예시 핵심: assembler는 각 object file에 자신이 정의하거나 참조하는 함수·전역 변수의 symbol table을 만든다. `main.c`에서 `sum`은 external reference이고, `sum.c`에서 `sum`은 global definition이다. `array`는 `main.c`가 정의한 전역 심볼이며 `sum` 호출의 첫 인자로 전달된다. linker는 symbol resolution으로 참조 `sum`을 정의 `sum`에 연결한다. relocation은 최종 executable의 section과 심볼 주소가 정해진 뒤 참조 위치를 고친다.

### Part 3

11. 예시 답:

```c
long f(long b) {
    long mask = 0xFF00;          // constant folding
    long a = (b << 2) + b;       // strength reduction
    return a + mask;
}
```

`0xFF << 8`은 상수 입력만 가지므로 compile time에 접을 수 있다. `5b = 4b+b`이고, `4b`는 `b << 2`로 표현할 수 있다.

12. 예시 답:

```c
void set_norm(long i) {
    vec_t *elem = &v[i];
    long x = elem->x;
    long y = elem->y;
    norm[i] = x * x + y * y;
}
```

`v[i]` 주소 계산과 멤버 dereference를 재사용한다. 실제 생성 코드는 aliasing·register allocation을 고려하지만, 공통 부분식을 명시적으로 제거한 형태다.

13. 예시 답:

```c
int func(int y) {
    int tmp = 0;
    if (y != 0) tmp = y - 1;
    if (y != -1) tmp += y;
    return tmp;
}
```

`pred(0)`은 0으로 접히고, 불필요한 `+0`과 항상 참인 분기는 제거된다. call/return, return address, 인자 전달 비용을 줄일 수 있다. 반대로 함수 본문을 여러 호출 지점에 복사하면 code size가 커져 instruction cache와 디버깅에 불리할 수 있다.

14. A만 가능하다. `n`과 `i`가 루프 동안 바뀌지 않으므로 다음처럼 쓴다.

```c
long ni = n * i;
for (long j = 0; j < n; j++)
    a[ni + j] = b[j];
```

B는 매 반복에서 `i`를 변경하므로 `n*i`가 loop invariant가 아니다.

15. 예시 답:

```c
size_t i = 0;
for (; i + 3 < nelts; i += 4) {
    A[i]   = B[i]   * k + C[i];
    A[i+1] = B[i+1] * k + C[i+1];
    A[i+2] = B[i+2] * k + C[i+2];
    A[i+3] = B[i+3] * k + C[i+3];
}
for (; i < nelts; i++)
    A[i] = B[i] * k + C[i];
```

루프 제어·branch의 빈도를 낮추고 CSE나 code motion 기회를 늘릴 수 있다. 반면 code size가 커지며 instruction cache 압박 때문에 항상 빨라지는 것은 아니다.

16. `lower1`은 매 반복 `strlen`이 최대 O(n)이므로 전체 O(n^2)이고, `lower2`는 `strlen`을 한 번만 호출하므로 O(n)이다. 사람이 문자열 길이가 변하지 않음을 확인했다면 `n`을 미리 저장하는 것이 유리하다. 그러나 컴파일러는 일반 함수 호출, 별칭, side effect를 보수적으로 판단해야 하므로 동일한 변환을 항상 보장할 수 없다.

17. `INT_MAX - (-1)`은 signed overflow를 일으킨다. C에서 그 연산의 동작은 정의되지 않았으므로 최적화기는 overflow가 발생하지 않는 유효한 실행만 전제로 `a-b > 0`을 참으로 볼 수 있다. 따라서 안쪽 조건을 제거할 수 있다. 하드웨어가 우연히 2의 보수 wraparound를 보인다고 해서 이 C 프로그램의 결과를 이식성 있게 단정할 수는 없다.

18. `R_X86_64_32 array`는 `%edi`에 들어갈 첫 번째 인자 `array`의 주소를 고치는 entry이고, `R_X86_64_PC32 sum-0x4`는 `callq`의 `sum` 참조를 고치는 entry다. `%esi`에는 두 번째 인자 `2`가 들어간다. x86-64 System V 호출 규약에서 첫 두 정수/포인터 인자는 `%rdi`, `%rsi` 계열이다. displacement는 target - next-PC이므로 `0x4004e8 - 0x4004e3 = 5`다.

19. `main.o`에서 `shared`와 `main`은 global definition, `helper`는 local definition, `sum`은 external reference다. `sum.o`에서 `sum`은 global definition이다. `helper`는 `static`이므로 `main.c` compilation unit 내부에서만 보이며 external symbol로 제공되지 않는다. 따라서 다른 object file은 `helper`를 해결할 수 없다.

20. 예시 답:

```sh
ar rcs libvector.a addvec.o multvec.o
gcc -static -o prog2c main2.o -L. -lvector
ldd prog
```

`ar`는 object file들을 인덱스가 있는 archive로 묶는다. `gcc -static`은 필요한 라이브러리 코드를 실행 파일에 포함하도록 링크한다. `ldd`는 동적으로 링크된 `prog`가 load-time에 요구하는 shared library를 확인한다.

### Part 4

21. 이 코드는 안전한 signed overflow 검출식이 아니다. `x == INT_MAX`에서 `x+1` 자체가 signed overflow이며 C 의미론에서는 정의되지 않은 동작이다. 따라서 최적화기는 비교가 항상 거짓이라고 단순화할 수 있다. 덧셈 전 범위를 검사하거나, 요구사항에 맞는 unsigned 연산·컴파일러 내장 overflow 검사 기능을 사용해야 한다. `-fwrapv`는 GCC의 특정 의미론 선택이지, 임의의 C 코드가 안전하다는 일반 보장은 아니다.

출처: GCC, *Code Generation Options* (`-fwrapv`, `-fstrict-overflow`)
https://gcc.gnu.org/onlinedocs/gcc/Code-Gen-Options.html

22. `sum.c`의 `static sum`은 local definition이므로 다른 object file에 export되지 않는다. `main.o`에는 external reference `sum`이 남고, linker는 이를 해결할 전역 정의를 찾지 못해 undefined reference 오류를 낸다. 여러 파일에서 호출해야 하는 API에는 `static`을 붙이지 않고 선언과 정의의 타입을 일치시킨다. 반대로 파일 내부 구현 세부사항만 사용하는 함수·전역 변수에는 `static`을 사용해 external symbol table을 불필요하게 오염시키지 않는다.

출처: SEI CERT C, *DCL19-C. Minimize the scope of variables and functions*
https://wiki.sei.cmu.edu/confluence/display/c/DCL19-C.+Minimize+the+scope+of+variables+and+functions

23. `unknown(s)`가 `s` 또는 `s`가 가리키는 메모리를 읽거나 바꾸지 않는다는 보장이 없으므로, 호출을 한 번만 수행하도록 밖으로 옮기면 호출 횟수와 결과가 달라질 수 있다. 루프 본문도 `s[i] = 0`으로 관련 메모리를 바꾼다. 안전한 code motion을 하려면 매 반복의 `unknown(s)` 결과가 같고 호출의 관찰 가능한 side effect가 없음을 증명해야 한다. 이 증명에는 함수의 pure/const 성질과 함수 경계를 넘는 modification/reference 분석이 필요할 수 있다.

출처: GCC, *Optimize Options* (`-fipa-pure-const`, `-fipa-modref`)
https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html
